# 单元测试

## 定位

`unit-test` 验证复杂内部逻辑是否正确，使用 Mock 数据隔离外部依赖。没有真实 API 入口且
内部行为复杂时，它可以作为主测试；功能具有 API 入口时，只有集测难以低成本穷举的复杂
内部逻辑才按风险补充单测。是否存在 API 入口和当前环境是否可用，都不能单独触发单测。

单元测试定位为白盒测试：以业务规则为中心，结合代码结构、分支、条件、异常路径和下游参数
转换，验证当前单元中与风险匹配的关键有效路径是否正确。

单元测试不验证真实 Spring 装配、真实 DB、真实 Redis、真实 MQ、真实外部系统或完整 API 链路；这些进入 `it-test`。

需求级用例定义业务预期；单元测试结合代码结构补充高风险有效路径，不得反向修改已确认预期，也不能替代真实 API 灰盒集成测试。

## 触发条件

出现以下任一情况时使用：

1. 定时任务、消费者、内部处理器或其他功能没有真实 API 入口，并包含复杂算法、多分支、
   状态流转、并发、难穷举边界或重要异常处理。
2. 核心方法或组件承载复杂业务规则，并被多个 API、定时任务、消费者或其他入口复用，需要
   用白盒反馈保护各入口共享的内部契约。
3. API 实现包含集测难以低成本穷举的复杂算法、分支组合、状态机或下游调用编排；此时单测
   只作为真实 HTTP 功能集测的补充，并根据风险和回归价值选择，不固定使用。
4. 真实 HTTP 已到达被测服务且失败确认来自复杂内部行为，但仅靠灰盒反馈无法高效定位或
   穷举；连接拒绝、服务未启动、鉴权缺失或依赖不可用等环境失败不触发单测回退。
5. 已有单测承担本轮受影响的复杂内部契约，需要继续运行或补充其高风险路径。

简单字段赋值、一对一映射、CRUD、薄编排、直接条件判断或明确返回结构，无论是否存在 API
入口，都不为覆盖率、测试先行形式或环境不可用新增单测；使用主验收、已有测试、直接调用、
编译或静态检查中的适合证据。API 的请求、响应、鉴权、数据和副作用属于集测职责，API 功能
回归不能只补单测。

## 反馈与实现顺序

单测触发后，先判断它承担测试先行还是补充验证：

1. 先根据测试用例、已有测试、当前代码和业务规则确认命中上述复杂性条件；未命中时返回
   调用入口选择主验收，不新增单测。
2. 已有测试完整覆盖时直接复用，修改前运行并确认通过。
3. 旧行为缺少保护时先补测试，修改前应通过，用于锁定既有行为。
4. 测试先行有价值时，新内部逻辑或 Bug 路径先写能锁定预期的测试，运行并确认因目标行为
   缺失或错误而失败。
5. 写最小生产代码并保持旧行为测试通过，运行新增或受影响单测直到高风险路径均有覆盖。
6. 需要整理代码时，只在测试通过后重构，并保持测试通过。

API 功能已选择测试先行时，先由集测建立外部契约 Red；确认复杂内部逻辑确实需要白盒保护
后，再按风险建立对应基线。未选择测试先行时，单测也只能作为复杂内部逻辑的补充证据，最终
API Green 仍由真实集测证明。没有 API 入口的复杂内部行为命中本 Skill 时，再决定先建立 Red
还是实现后完成白盒验证。旧行为保护测试应在修改前通过，不能伪造成 Red。

## 白盒测试设计

测试设计必须先阅读当前要验证的代码单元，按业务规则反推测试路径：

1. 识别入口方法、关键分支、条件组合、循环、异常处理、默认值和边界值。
2. 识别每条路径对应的业务规则、输入条件、下游调用、返回结果或状态变化。
3. 自动选择合适的白盒覆盖策略，不机械列术语，不为了覆盖率制造无业务意义用例。
4. 对会改变业务结果、下游参数、异常类型、状态流转或持久化意图的路径，必须有测试。
5. 对不可达路径、无业务差异路径、框架样板代码，可以说明不测原因。

有效测试路径的判断标准：输入条件或代码路径不同，会导致返回值、异常、下游参数、状态变化、日志审计或业务副作用中的至少一项不同。

## 覆盖停止条件

只有满足以下条件，才能认为单元测试设计完成：

1. 每个触发单测的高风险规则或路径都有对应测试。
2. 相关关键条件、异常和边界路径都有有效断言。
3. 下游调用参数是业务结果的一部分时，已验证关键字段。
4. 已说明仍由灰盒集测覆盖或未覆盖的路径及原因。

## Mock 规则

1. 单元测试允许全 mock 外部依赖。
2. 只 mock 当前测试边界之外的依赖，不 mock 本轮要验证的逻辑。
3. Mock 返回值只服务当前路径，不构造无关大对象。
4. 下游调用参数是验收点时，必须用捕获器或等价机制验证关键字段。
5. 打印结果不能替代断言。

## 测试数据

单元测试数据可以 mock，但必须符合业务逻辑：

1. 枚举、状态、类型、长度、必填字段必须来自代码、常量、已有测试、配置或明确需求。
2. id、账号、时间、金额等可以使用稳定假数据，但不能与业务规则冲突。
3. DTO、VO、PO 字段只填当前路径必要字段。
4. 无法确定合法值时，先从代码和已有测试确认；仍不确定再询问用户。

## 测试文件规则

单元测试文件使用 `*Test` 后缀，包路径优先跟随被测 Service、业务类、通用组件或项目已有测试约定。

测试文件优先对应被测文件，例如 `UserServiceTest` 对应 `UserService`。当已有测试文件已经庞大、包含过多无关节点或继续追加会降低可读性时，按业务功能、接口域或方法域拆出新的测试文件，不把所有场景继续塞进巨型测试类。

测试类内部使用 `@Nested` 内部类表达测试节点。一个节点对应一个业务方法、通用/公共方法或明确功能点；节点内再按回归测试、新增需求、异常场景、边界场景等组织测试方法。

使用 `@DisplayName` 说明中文业务场景，使用 `@Tag("regression")`、`@Tag("feature")`、`@Tag("exception")` 等标记测试性质。单元测试偏向给 AI 和后续维护者定位业务逻辑，不要求每个小方法都强行多层嵌套，但新增测试必须有清晰节点和场景说明。

1. 优先追加到已有合适测试类，不新建重复测试类。
2. 新测试类位置、命名、框架和断言风格跟随项目已有约定。
3. 方法级别必须有简短注释或 `@DisplayName`，说明场景和期望。
4. 测试方法名表达业务行为，不使用 `test1`、`testSuccess` 这类空泛命名。
5. 新增、删除、修改测试方法时，同步维护测试类已有场景说明、内部类分组或注解标记。

## 内部逻辑回归保护

修改由本 Skill 承担的复杂或多入口复用旧逻辑时，先查找已有单元测试。

1. 如果旧行为没有测试，先补回归测试锁定旧行为，再新增二开功能测试。
2. 新增旧行为保护测试后必须先运行，确认修改前通过。
3. 如果已有回归测试，默认不允许修改原有回归测试。
4. 新内部规则必须新增测试方法、测试节点或测试类，不能通过改旧回归测试制造通过。
5. 只有需求明确改变旧功能时，旧回归测试才允许修改；修改前必须说明哪个旧预期失效、为什么失效、新预期是什么。
6. 回归测试和新增测试必须通过 `@DisplayName`、`@Tag` 或内部类分组区分，方便后续定位。
7. API 功能的旧行为和 Bug 回归必须由集测覆盖；内部逻辑单测只能作为补充，不能替代 API 回归集测。

## 失败处理

测试失败后先读完整错误信息，按顺序判断：

1. 测试数据是否不合法。
2. Mock 是否缺失或边界错了。
3. 断言是否表达错了需求。
4. 生产代码是否确实不符合预期。

禁止删除断言、放宽断言、跳过测试或 mock 掉目标逻辑来制造通过。

## 输出要求

完成后说明：

1. 新增或修改的测试方法。
2. 每个方法覆盖的业务规则、代码路径和关键断言。
3. 明确未覆盖路径及原因。
4. 实际运行的测试命令和结果。
5. 单测作为 API 补充还是无 API 功能主测试的判断依据。
