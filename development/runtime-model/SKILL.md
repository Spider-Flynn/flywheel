# Runtime Model

## 定位

从已有软件项目的实际代码中还原项目当前如何运行，将分散的实现事实提炼为稳定的业务
对象、能力模块、生命周期、端到端流程和系统边界，最终生成一份不依赖读者直接阅读代码的
《项目核心运行模型》。

代码是主要证据源，而不是文档组织方式。最终文档描述项目的上层模型，不把包、类、表、
接口或页面目录换一种格式罗列出来。

与相邻能力保持以下边界：

- 只基于业务材料和持续问答深化业务认知时，使用 `biz`。
- 为未来功能、新模块或跨系统改造产出方案时，使用 `design`。
- 回顾一次已完成需求的设计、开发、结果、个人贡献和面试表达时，使用 `recap`。
- 只解释单个模块、类或调用链时，直接执行局部代码分析，不生成全项目模型。

## 证据边界

使用以下优先级组织事实：

1. 当前仓库中可达的实现、调用关系、状态变化和真实数据读写。
2. 与主链直接相关的配置、定时任务、消息消费、外部集成和测试事实。
3. 用户提供的业务文档、前端观察、运行结果和已确认业务规则。
4. 必要且获得授权时的只读数据库结构或最小数据样本。

注释、README、目录名称和界面文案可以提供线索，但不能单独证明实际运行关系。活跃实现、
已停用实现和未接通的能力要分别处理，不把“代码存在”直接改写成“系统正在使用”。

为每个实质结论保留内部证据指针，但用户未要求时不把类名、文件、表名和调用链写入最终模型文档。无法证实但仍会影响整体模型的关系使用
`[待确认]` 标记；只符合领域常识但没有项目证据的内容不进入项目模型。

## 执行

### 1. 确定范围和交付

先读取目标仓库的现行规则，确认目标项目、相关仓库、已有材料、输出路径和禁止事项。已有信息足够时直接继续；只有多个仓库的主从关系、
项目边界或覆盖范围不同会实质改变文档时才询问用户。

默认只读分析仓库并新建 `docs/项目核心运行模型.md`。用户已指定文件或要求优化现有文档时
使用指定目标。不修改生产代码、数据库和外部系统。

### 2. 建立项目证据地图

如果目标仓库已经建立 CodeGraph 索引，按仓库规则优先用它定位符号、调用链和影响范围；未建立时使用文件和文本搜索，不自行创建索引。

先盘点而不是逐文件通读：

- 对外入口、定时任务、消息入口和外部集成；
- 核心业务对象、持久化关系和状态字段；
- 主要业务编排、跨域调用和异步回调；
- 搜索、缓存、消息、文件存储和外部平台的职责；
- 相邻仓库中承担定时生产、数据接入或外部执行的部分。

为后续验证保留“候选能力 → 核心对象 → 入口 → 主要调用 → 数据去向 → 外部依赖”的精简证据地图，不保存全量源码摘录。

### 3. 按稳定对象形成候选模块

以核心对象、生命周期、完整职责和上下游关系划分能力模块。目录、包、Controller、数据表、
前端顶层标签和页面页签只能作为入口线索，不直接定义业务模块。

优先识别四类对象：

- **能力定义**：规则、流程、策略、订阅、调度等尚未执行的定义。
- **运行实例**：订单、任务、事件、工单、告警、报告等已发生的对象。
- **知识与上下文**：分类、标准、资产、组织、标签和辅助信息。
- **平台能力**：公共语义、权限、接入、发布、存储和外部集成。

同名对象需要通过身份、状态和关联关系确认是否共享模型；不同名对象若共享一个生命周期，则应归入同一能力域。

### 4. 验证纵向业务链

为每个候选模块至少验证一条从入口到结果的代表性链路，回答：

1. 谁或什么系统提供输入；
2. 哪个对象承载这次处理；
3. 对象经过哪些关键状态和动作；
4. 哪些环节是同步调用、异步消息或周期调度；
5. 最终生成什么结果，谁消费该结果；
6. 数据和执行能力属于目标项目还是外部系统。

不只读取列表查询和 CRUD；优先追踪创建、发布、转换、绑定、处理、回调、关闭、定时生产和结果回写等会改变对象生命周期的行为。

### 5. 构建横向协作模型

将纵向链路组合为项目整体模型：

- 确定项目的核心业务闭环；
- 区分主干能力、专业支撑域和平台底座；
- 连接模块之间的供给、消费、触发、回写和反馈关系；
- 区分目标项目负责的定义与编排，以及外部引擎或平台负责的数据生产与动作执行；
- 说明关系存储、搜索、缓存、消息和文件等运行机制在业务流中的职责；
- 将未发现真实调用的候选关系保留为未闭合边界，不强行连线。

### 6. 生成非代码化项目文档

根据项目实际结构自然组织文档，只保留对整体模型有价值的内容。通常要覆盖：

- 项目定位和责任边界；
- 总体能力架构和核心运行模型；
- 核心对象、对象关系和主要生命周期；
- 各能力模块的职责、输入、运行和输出；
- 数据与运行架构；
- 端到端核心流程；
- 模块协作关系与系统内外边界；
- 统一运行机制和仍影响整体模型的未闭合关系。

不为满足固定目录而填充空洞章节。文档中不保留：

- “为什么不按菜单或目录划分”等建模方法辩护；
- 新人阅读顺序、代码阅读路径和后续学习计划；
- 常见误区、页面到模块映射和文档编写说明；
- 类名、方法名、包路径、表名、配置键和接口清单；
- 调试、搜索和证据回收过程；
- 不影响模块职责、对象语义或系统边界的实现细节。

只在技术机制会改变项目责任或运行语义时保留必要的技术抽象，例如异步执行、周期快照、搜索与事务数据分离、外部系统执行。

## 验证

交付前从最终文档本身重新审计：

1. **项目视角**：每个章节都在回答项目是什么、有什么对象、如何运行或边界在哪；删除面向文档作者和读者的元叙事。
2. **抽象层级**：模块由稳定对象、职责和生命周期定义，不是源码目录、前端标签或数据表的一比一翻译。
3. **链路完整性**：每个核心模块都有输入、核心对象、关键处理、输出和上下游；所有关键跨模块连接都有实际证据。
4. **边界完整性**：区分项目自身与外部引擎、数据平台、定时任务、组织服务和通知服务的责任。
5. **事实可追溯**：实质结论可回到已读取的代码或授权材料；未闭合关系没有被写成当前事实。
6. **非代码化**：正文不包含代码、实现标识符、详细 API 或表结构，除非用户明确要求证据附录。
7. **信息收敛**：合并重复的概述、流程和总结，删除不改变项目模型的实现颗粒。

使用与仓库风险匹配的文档和结构检查完成验证；用户未要求时不因产出文档而运行业务服务、
调用写接口或修改数据。最终说明新建或修改的文档、实际执行的检查，以及仍影响整体模型的
未闭合边界。
