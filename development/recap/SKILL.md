# Recap

## 目标

基于当前会话及其中已经形成的业务、设计、测试和开发产物，复盘本次需求从理解到结果的
完整过程。先通过交互补齐最终文档所需的信息，再产出一份供用户长期回顾、未来 Agent
理解项目的中文 Markdown 文档。

## 交互流程

### 1. 自主理解与复述

先完整回顾会话，按下文的成文主线自行连接已有信息，再向用户给出一版连贯复述，同时指出
仍然影响完整复盘的缺口。按需求的真实来由交代背景：独立需求直接说明自身；源于前序需求
或遗留问题时说明二者关系；设计过程中进一步发现的问题放在设计分析中展开。

### 2. 补齐与校准

让用户先修正这版理解，再以最终文档为目标询问仍然缺失的信息。只问无法从现有上下文确定、
且会影响业务理解、数据边界、设计理由、开发过程、最终效果、职责归属或经验沉淀的内容；
相互关联的问题一并询问。

根据用户校准持续更新理解。内部区分会话中已有的信息、用户补充、合理推断和仍然未知的
内容；用户无法补充时保留未知边界。获得最终文档所需信息，或确认剩余信息确实无法获得后，
再生成文档。

## 文档组织

文档沿本次需求实际发生的因果顺序向下展开：

```text
业务与本次需求
→ 系统、数据和职责边界
→ 设计分析中发现的问题
→ 方案选择、取舍与边界
→ 开发和测试过程
→ 实际问题、修正与验证
→ 最终效果与项目成果
→ 个人职责与经验沉淀
→ Agent、Skill 与 Harness 反思
```

这条顺序用于保证全文能够从需求讲到结果，不是固定目录。章节名称、篇幅和合并方式由项目
实际内容决定。

最终文档的各级标题统一使用阿拉伯数字分级编号：一级标题使用 `1. 标题`、`2. 标题`，
二级标题使用 `1.1 标题`、`1.2 标题`，后续层级按相同规则递进。

业务、数据和职责边界要为后续设计提供依据；设计过程要说明发现了什么问题、为什么选择
当前方案以及舍弃其他方案的理由。结果部分以需求目标收口，说明实际解决了什么、达到预期
的程度、关键风险如何得到控制，以及能够确认的量化或非量化效果。

未来 Agent 所需的项目认知由上述业务、数据和设计叙事自然承载。写清当前仍然有效的规则，
并为只属于本次需求的历史问题、一次性方案和过程决策保留语境与时间边界。

经验沉淀同时覆盖业务认知、技术方法、工程方法和 AI 协作。结合会话中的真实交互，说明
Agent、Skill 或 Harness 哪些做法有效，哪里发生规则未执行、用户纠正、上下文传递或流程
失配，问题为什么发生，以及可以怎样迭代；形成可迁移判断，而不是罗列工具名称。

## 表达约束

文档按事实自然叙述本次需求，个人职责按用户实际贡献使用第一人称，后续可选材料同样按事实
叙述。合理推断使用有边界的表述，未知信息保持未知。允许润色和重组表达，但不虚构需求、
设计、问题、结果或个人贡献。

## 可选产出

复盘文档完成后，用户需要简历或面试材料时，读取 `references/resume-interview.md` 补齐。
这部分不在默认产出内，用户没有要求时不生成。
