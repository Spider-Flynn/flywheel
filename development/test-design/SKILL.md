# 测试设计

## 定位

`test-design` 负责把已确认的设计事实转换成需求级测试用例，回答“哪些场景和结果能够证明新需求正确，并且受影响的旧行为没有被破坏”。

本 skill 可以只读接口契约、既有行为和必要代码来补足事实，但不选择单测、集测或其他测试实现方式，不编写或修改测试代码、生产代码。

## 输入门禁

开始前确认：

1. 已提供 `design.md` 或 `docs/powers/` 下存在对应设计产物。
2. 设计中的功能规则、接口契约和当前范围已经确认。
3. 阻塞测试预期判断的待办已清除，或已明确排除在当前范围之外。
4. 二开功能能够获取已有接口、既有行为或必要代码入口。

设计事实不足时返回 `design`，不要在本 skill 中猜测需求或修改设计。

边界清楚的小需求可以只在当前会话确认测试场景，不强制单独调用本 skill 或产出文件；仍应复用本 skill 的用例判断原则。

## 信息来源顺序

1. 已确认的功能规则和接口契约。
2. 用户明确说明的输入、输出、限制和验收预期。
3. 已有接口行为、必要代码实现和相关数据结构。
4. 测试环境、真实数据、请求上下文和外部依赖条件。

二开时优先读取已有契约和行为资料。只有这些信息不足以判断受影响行为时，才读取与当前范围直接相关的代码；不要展开无关代码探索。

## 测试设计流程

1. 读取完整设计产物，按功能单位列出规则和接口。
2. 为每条新功能规则设计正常、边界、异常、权限、状态和副作用场景。
3. 二开功能识别本次可能影响的既有行为，形成回归范围。
4. 发现既有行为与当前设计冲突时，返回 `design` 或请用户确认，不自行选择预期。
5. 明确测试数据、Header、Cookie、token、权限、环境和副作用前提。
6. 多个功能或接口边界清楚、互不依赖时，调用 `subagent` 分节点生成草稿；每个节点使用唯一输出路径。
7. 汇总全部功能草稿，检查跨功能遗漏、重复和冲突。
8. 收集全部待确认问题，给出建议和影响，一次性集中向用户确认。
9. 根据用户集中回答统一修正。需要跨阶段保存稳定测试规格时，才读取 `assets/test-case-template.md` 并产出或更新最终测试用例文档；只在当前会话确认轻量测试预期时不加载模板。

## 集中确认规则

1. 不要完成一个功能就立即向用户提问；先继续处理其余可执行功能。
2. 每个待确认项必须包含所属功能、问题、建议答案和不确认的影响。
3. 能够基于建议继续时，先保留明确的临时标记，不把建议写成已确认结论。
4. 所有功能草稿和主会话复核完成后，对问题去重、合并并一次性询问用户。
5. 用户回答后，同步更新所有受影响用例，并删除已解决的临时标记。
6. 只有缺少共同事实导致所有剩余测试设计都无法继续时，才允许提前阻断并询问。

Sub-agent 只返回问题和建议，不直接与用户逐项交互。主会话负责集中确认和最终结论。

## 用例编写规则

每条用例必须包含：

1. 用例 ID 和对应设计规则。
2. 用例性质：新功能、回归、Bug、异常、权限、边界或状态。
3. 前置状态、测试数据和请求上下文。
4. 输入或操作。
5. 预期响应或异常。
6. 预期数据、状态和关键副作用。
7. 必要的清理、回滚和重复执行要求。

预期结果必须可判断。动态时间、随机 ID、异步结果等无法写死时，写判断规则、范围或最终状态，不伪造固定值。

需求级用例只描述业务场景和可观察预期，不展开 Java 测试类、Mock 写法、代码分支或测试实现类型。后续执行者自行选择如何把用例落实为测试代码。

## 回归规则

1. 回归范围只覆盖本次修改可能影响的既有行为，不扩张为全系统补测。
2. 既有行为缺少明确验收场景时，先设计旧行为保护用例，再设计新功能用例。
3. 只有已确认需求明确改变旧预期时，才允许更新对应回归用例，并写清当前有效预期和依据。

## 文档命名与维护

需要稳定保存的测试用例产物默认放在 `docs/powers/`：

1. 单功能或内容较少时，使用 `功能名/模块名 + 测试用例.md`，例如 `资产查询测试用例.md`。
2. 多个独立功能内容较多时，使用 `模块名测试用例/` 文件夹，每个功能一个测试用例文件，由主会话维护简短的 `总览.md` 和跨功能用例。
3. Sub-agent 草稿不作为最终产物；主会话汇总完成后删除或移出 `docs/powers/`。

文档只保留当前有效的测试用例和未满足条件，不记录讨论过程。设计发生变化时，先更新 `design.md`，再同步更新受影响用例；没有重新确认前不得把旧用例当作当前验收基线。

## 完成门禁

完成前确认：

1. 每条功能规则都有测试用例。
2. 受影响的旧行为都有回归判断。
3. 每条用例的输入、前置条件和预期可执行、可判断。
4. 测试数据、请求上下文和副作用条件已确认。
5. 用户已经确认测试预期。
6. 多节点结果已由主会话完成去重、冲突检查和跨功能复核。

## 禁止事项

1. 不要编写或修改测试代码、生产代码。
2. 不要根据当前实现反向修改需求预期。
3. 不要为了数量机械生成无业务差异的用例。
4. 不要把内部代码分支直接当作需求级验收结果。
5. 不要在预期冲突时擅自修改旧测试。
