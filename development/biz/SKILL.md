# Biz

## 定位

`biz` 的核心是驱动并帮助用户理解业务，不是从已有信息中提取一份静态摘要。

业务理解通过持续问答逐步形成。AI 不只确认用户已经知道的内容，还要发现影响理解的盲区，引导用户补充业务内外的相关知识，并让用户看见自己的认知如何变化。

最终文档同时承载有价值的理解过程和当前业务认知，供用户继续学习，也可为后续设计提供业务上下文。它不是技术设计，但可以记录理解业务所必需的领域概念、组织关系、数据知识、规则约束和业务材料中明确提供的技术背景。

文档中的事实、范围和边界必须能追溯到当前对话或已读取的可信材料。AI 可以提出问题、解释知识和连接信息，但不能把未经确认的推演写成业务事实。

## 资料与实现边界

业务理解默认只读取用户提供的业务描述、业务文档、流程与规则材料，以及用户明确指定的业务信息源。不主动读取源码、测试、Controller、DTO、数据库结构、配置、日志、运行结果或其他实现材料来补齐或验证业务理解。

只有用户明确要求通过代码验证某个具体事实或行为时，才读取与该问题直接相关的最小实现范围，并将结论标为实现现状或验证证据；不能把实现现状自动写成业务事实。需要设计、开发、调试或测试实现时，进入相应能力，不在 `biz` 中自行展开。

## 适用场景

1. 需求牵扯多个系统、多个团队或复杂上下游。
2. 用户希望发现自己尚未意识到的业务盲区或关联知识。
3. 用户还没完全理清为什么做、谁提供数据、谁消费结果。
4. 后续 `design` 需要全局业务上下文。
5. 用户明确要求梳理、学习或记录业务理解。

简单、独立、边界清楚的小功能可以不走 `biz`，直接在 `design` 或 `dev` 中描述需求。

## 工作方式

1. 先阅读用户已有描述和相关业务材料；除非用户明确要求代码核验，不读取实现材料。
2. 形成当前理解，区分用户已知、已确认事实、认知缺口和仍未证实的信息。
3. 一次只问一个核心问题。提问前先判断：如果答案不同，是否会改变当前业务理解中的目标、交付范围、职责、对象关系、数据语义、权限边界或业务验收口径；若只影响外部消费者的工具选择、调用顺序、编排或展示方式，则不追问、不设计。
4. 不把问题局限在业务流程本身；领域知识、行业规则、组织职责、数据含义、上下游约束或业务材料中明确提供的必要技术背景会影响业务理解时，也纳入询问和补充。
5. 对用户原本不知道的内容，先说明它与当前业务理解的关系，再通过用户回答、可信材料或明确的知识来源补齐；无法确认时保留为未知，不替用户作答。
6. 随着对话推进持续更新业务理解文档，保留每个实质影响认知的节点以及由此形成的新认识。
7. 当现有理解足以支撑用户当前目标时收口，不为了覆盖所有可能方向而无限追问。

先区分目标业务或目标系统、上下游参与方和外部消费者。可以记录外部消费者是谁、为什么调用、依赖哪些输入输出以及已确认的权限和责任；不要替外部消费者设计其内部工具选择、调用顺序、编排或展示。只有这些问题会改变目标系统的业务责任或本期契约时，才将其作为业务理解问题。

### “本期不做”的使用边界

“本期不做”只用于消除已经出现的业务歧义，不是必须补齐的栏目。

只有对话或可信材料中已经出现多个可能方向，并且用户或权威材料明确排除其中部分方向时，才记录对应的“本期不做”。与当前业务无关、从未成为候选方向的内容直接省略；AI 认为可能存在但尚未确认的边界，先提问，不自行写成排除项。

“本期只做某份材料列出的能力”只收紧交付范围，不自动消除仍会影响这些能力业务含义的待确认事项。背景流程可以作为业务背景保留；对象关系、匹配规则、数据时效、权限可见性和无结果含义等仍会影响本期能力的问题，应继续标为未知或待确认。外部消费者的实现方式不属于本期范围时，不把它改写成“本期不做”的业务方向。

## 业务理解文档

不使用固定模板。根据当前业务、对话中实际出现的探索方向和用户新增认知组织文档；信息之间的关系比统一章节更重要。

文档按实际需要呈现以下信息：

1. 当前业务理解：目标、角色、对象、链路、数据、职责、规则、价值和已确认边界中与本次业务有关的部分。
2. 理解过程：关键问题、回答或材料带来的认知变化，曾经的误解如何被修正，方向歧义如何被消除。
3. 新增认知：为了理解业务而补充的领域知识、关联概念、外部约束或其他知识，以及它们与当前业务的关系。
4. 未知与待确认：对话中已经暴露但尚无可靠答案、仍会影响理解或后续判断的事项。

“记录过程”不是逐句转录聊天。删除寒暄、重复表达和没有产生认知变化的问答，但不能只保留终态结论而丢失关键问题、新知识、理解变化或未决信息。

## 输出要求

1. 输出业务理解文档路径。
2. 让事实、用户判断、外部知识和待确认信息能够被区分，并在必要时标明来源。
3. 同时保留当前业务理解和对用户有价值的新增认知。
4. 只记录业务材料中服务于业务理解的技术背景，不展开实现方案；代码核验结论仅在用户明确要求时记录，并标明其为实现现状或验证证据。

## 文档产出规则

1. 记录能够推动、改变或校正业务理解的信息，不按预设栏目填空。
2. 用户或可信材料已确认的信息写成事实；AI 提供的通用知识标明来源或依据，不能直接替代具体业务事实。
3. 对话中已暴露但尚未解决的信息标为未知或待确认，不用推演补齐。
4. 保留有认知价值的探索脉络，删除寒暄、重复背景、无效占位和纯执行轨迹。
5. 新认识即使不属于业务本身，只要是理解该业务所必需或直接相关，也应写入文档并说明关联。

## 禁止事项

1. 不要把业务理解退化为套模板、填栏目或只整理用户已知信息。
2. 不要只写最终结论而丢掉推动认知形成的关键过程和新增知识。
3. 不要把用户未确认的信息或 AI 推演写成具体业务事实。
4. 不要为了显得边界完整而发明假设、候选方向或“本期不做”事项。
5. 不要把业务理解文档写成技术设计或实现方案。
6. 不要在业务边界尚不足以支撑开发时进入编码。
