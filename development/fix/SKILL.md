# Fix

## 定位

`fix` 聚焦 `debug + 修复闭环`。它处理已有功能实现不符合已确认需求、存在逻辑问题或没有遵守既有规则的行为，不承接新增功能开发，也不在根因不清时直接修改代码。问题在开发、测试、CR、上线前或上线后发现，不影响其 Bug 定位。

如果用户只要求定位和分析，使用 `debug` 并在根因与修复方案处停止，不执行代码修改。如果确认当前任务不是已有实现的纠错，停止 `fix` 并交回用户确认后续入口；`fix` 不直接决定后续功能开发入口。

## 输入检查

开始前确认：

1. 错误表现和原始触发路径。
2. 用户要求定位并修复，而不是只分析。
3. 正确预期的来源：需求、设计、测试、接口契约或用户确认。
4. 可用的日志、数据、环境和复现条件。

信息不足时先调用 `debug` 收集证据，不猜测修复。

## 修复流程

### 1. Debug

1. 复现问题或确认触发条件。
2. 沿调用链和数据流定位根因。
3. 用最小验证动作证明或推翻根因假设。
4. 输出根因、证据和影响范围。

没有可验证根因时停止，不进入代码修改。

### 2. 修复规格确认

确认：

1. 正确预期和错误行为之间的差异。
2. 最小修复范围和不能改动的行为。
3. 受影响的接口、数据、状态、副作用和既有规则。
4. 是否改变 `design.md` 或接口契约。

只确认会改变修复结果的歧义，优先逐项列明输入和预期行为。歧义尚未解决时，不自行扩展
匹配规则、返回契约或修复范围。

如果正确预期、设计事实或测试预期本身尚未稳定，停止 `fix`，说明缺口并交回用户确认后续入口。

### 3. 回归与测试先行判断

明确 Bug 的前置状态、输入、错误表现、正确预期和原始触发路径，先选择最终验收，再独立
判断是否需要测试先行。API 或 OpenAPI 行为变化只决定最终使用真实 HTTP 验收，不单独构成
修复前必须获得 Red 的理由：

1. 优先查找已有测试和真实触发证据，不能通过删除、放宽或随意改写旧断言掩盖 Bug。
2. 新增或改变 API、OpenAPI 的用户可观察行为时，以 `it-test` 的真实 HTTP 目标集测和相关回归作为最终 Green 验收。
3. Bug 涉及复杂业务规则、状态流转、错误处理、多入口复用、难稳定复现或高回归风险，且测试
   能稳定判断结果时，选择测试先行并说明命中的具体风险和价值。API、OpenAPI 先由
   `it-test` 获得目标 HTTP Red，再按风险用 `unit-test` 补充复杂内部路径；没有真实
   API 入口的功能使用适合的白盒测试获得目标 Red。
4. 输入校验、参数分流、局部短路、格式或时间展示、一对一字段映射、明确返回结构等简单聚焦修复，根因、预期和影响范围已有充分证据时，可以不先获得 Red；说明判断依据后进入最小修复，并保留最终验收。
5. 已选择测试先行时，运行测试并确认失败原因是目标 Bug，而不是数据、环境或测试本身错误；API Red 因服务未启动、连接失败、鉴权缺失、依赖不可用或启动存在未授权副作用而无效时，按“失败与回流”处理。

### 4. 最小修复

1. 加载 `coding-standards`。
2. 只修改根因对应的最小范围，不做无关重构。
3. 选择测试先行时运行失败测试并确认修复后通过；未选择时运行已确定的最小充分反馈。
4. API 功能调用 `it-test`，通过目标集测和相关回归一次验证原始触发路径、鉴权、数据、
   状态和副作用；非 API 功能运行已选择的主反馈和相关回归，验证其原始任务或内部触发路径，
   只有触发 `unit-test` 时才以目标单测作为主反馈。
5. 运行新增或受影响的补充单测。
6. 运行项目编译命令。

## 失败与回流

- 确认当前任务不是已有实现的纠错，或上游预期存在缺失、冲突：停止 `fix`，说明依据并交回用户确认后续入口。
- 数据或环境条件不足：先判断它阻断的是必要的测试先行还是最终验收。复杂或高风险修复仍需测试先行时，说明阻断阶段、已有证据、未执行动作、需要用户补齐的条件和恢复位置，然后停止修改并等待；简单聚焦修复未选择测试先行，或新证据、用户确认使风险判断发生变化时，可以明确说明策略依据后完成最小修改和本地反馈，但最终验收仍保持阻塞，不能声称修复完成。
- 修复后仍失败：停止叠加修改，回到 `debug` 重新定位。

连续三次修复尝试失败时，停止继续修补，检查设计、架构、测试数据或环境前提。

## 验收门禁

完成前必须确认：

1. 原始问题已复现或触发条件已用证据确认。
2. 根因已验证。
3. 修复规格和正确预期已确认。
4. 选择测试先行时，Bug 回归测试已修复前失败、修复后通过；未选择时已说明简单性、现有证据和最终验收依据。
5. API 和 OpenAPI 的目标集测及相关回归集测已实际运行且通过。
6. 没有 API 入口且已触发 `unit-test` 时，目标单测及相关回归单测已实际运行且通过。
7. API 内部逻辑的补充单测已实际运行且通过；未触发时已说明判断依据。
8. 原始触发路径已验证。
9. 编译已实际运行且成功。
10. 未验证项、原因和残余风险已说明。

## 输出要求

说明：

1. 根因和证据。
2. 修复规格和修改文件。
3. 新增或复用的回归测试。
4. 实际运行的集测、单测、编译命令及结果，以及测试类型选择依据。
5. 原始触发路径验证结果、阻断阶段和当前状态；未获得最终 Green 时明确说明“已实现但验收阻塞”，不声称修复完成。

## 禁止事项

1. 没有根因就修改代码。
2. 把新需求伪装成 Bug 修复。
3. 删除断言、放宽断言、跳过测试或修改旧测试制造通过。
4. 已判断需要测试先行，却未看到目标 Bug 回归失败就修改生产代码。
5. 用单测代替 API 回归集测，或未验证原始触发路径和编译就声称完成。
6. 仅为绕过环境阻断，把仍有必要的测试先行改成其他测试或直接修改；风险判断确因新证据或用户确认发生变化时，必须明确更正依据，不能把无效 Red 当作修复证据。
