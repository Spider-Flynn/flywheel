# Coding Standards

## 定位

`coding-standards` 只定义开发场景下写代码时必须遵守的长期规范，不负责决定任务入口、拆解计划、测试策略或交付流程。

在实际修改代码前使用本规范；只读代码、解释方案或讨论设计时，不必加载。

## 通用开发原则

开发前必须先理解需求、阅读相关代码、分析问题，再说明实现方案。

执行时遵循：

1. 简单优先，选择最简单、最少改动、与现有项目一致的方案。
2. 保持一致，复用已有分层、对象、工具类、测试风格和文档风格。
3. 目标导向，关注需求是否完成、问题是否解决、验证是否成立。
4. 只修改当前任务需要的内容，不顺手重构、优化、升级依赖或调整无关风格。
5. 发现无关问题时先记录并说明，不直接修改。

禁止未分析直接修改代码、根据猜测修改代码、大范围试错、盲目重构。

## 信息缺失处理

开发需求进入编码前，如果出现明确的信息缺口，且当前上下文、记忆和已读材料中没有任何相关线索，先询问用户是否能提供文件路径、模块名、接口名、类名、需求文档、错误日志或信息来源。

不要在缺少入口线索时直接全量搜索、批量脚本扫描或大范围读取文件。用户通常比 AI 更了解项目，一次路径或模块提示往往比无差别搜索更高效。

只有在用户无法提供线索、授权自行探索，或任务本身就是要求做代码库梳理时，才扩大搜索范围。扩大搜索时也应先从最小关键词、入口目录和已知调用链开始。

## 工作区与提交边界

P0：所有修改代码的操作禁止在 `main`、`master`、`pre`、`test` 以及其他预发或测试相关分支上进行。开始修改代码前，如果当前目录是 Git 仓库，必须先确认当前分支；命中上述分支时停止修改并要求用户切换到开发分支。

未经确认不要主动 commit、push 或创建 PR。

禁止使用破坏性 Git 命令回滚用户改动。

禁止删除用户已有修改来制造干净工作区；遇到不相关的脏改动时记录并绕开，遇到相关冲突时先说明。

为了制造通过结果，禁止删除断言、放宽验证条件或跳过必要检查。

## CodeGraph 同步

修改代码后，完成前必须同步 CodeGraph 索引。

如果当前仓库没有 `.codegraph/`，先执行 `codegraph init -i` 主动建立索引，再执行 `codegraph sync`。

如果初始化或同步失败，必须说明失败原因、是否影响后续代码理解和验证结论。

## 注释规范

命名即文档，好命名胜过注释。命名必须精确一致、词达意，长度与作用域成正比：作用域越大，命名越要完整清晰；局部短生命周期变量可以更短。

注释补充代码无法充分表达的信息，包括业务职责、关键输入输出、业务边界、约束来源、异常语义和流程取舍。方法级注释可以说明方法负责什么及其边界；方法体注释重点说明为什么这样处理和非显然的流程步骤，不重复代码已经清楚表达的内容。

注释默认使用中文，保留 VO、DTO、PO、id、DB、Redis、MQ、API 等技术术语。

新建 Java 文件默认添加文件头注释：

```java
/**
 * @author: Flynn
 * @date: ${DATE} ${TIME}
 * @desc: 「描述文件功能」
 */
```

公共方法使用简洁 Javadoc。承担独立业务步骤、关键业务规则、非显然数据转换或异常语义的私有方法，也使用简洁 Javadoc，并按需说明关键输入、输出、业务边界和失败语义。简单转发、字段访问以及名称已经完整表达行为的工具方法不强制添加注释。

核心 Service 主方法使用连续步骤编号，修改代码时同步维护编号。主方法把业务步骤委派给子方法时，主方法注释说明该步骤在整体流程中的位置，子方法注释说明自身职责和关键边界；两者互相补充，不重复抄写同一内容。

禁止解释 Java 基础语法、为每行代码添加注释、写 AI 风格的大段说明、删除已有中文注释、保留与代码不一致的旧注释。

## Java 业务开发底线

外部输入必须防御式校验，重点关注必填非空、长度范围、枚举合法性、业务唯一键存在性和 DB 字段长度。

关键业务日志必须包含业务唯一标识，例如 userId、bizSeq、requestId。外部调用必须记录请求参数、响应和耗时。禁止明文打印手机号、身份证号、密码、token、密钥、账号凭证等敏感信息。

事务必须避免远程调用和大事务。注意 `@Transactional` 失效场景：同类内部方法调用、非 public 方法、异常被 catch 未抛出、回滚异常类型不匹配。

修改已有接口时必须检查入参、返回结构、字段含义和错误码兼容性。新增字段优于修改字段，保留旧接口。

写操作和状态变更必须考虑幂等，明确业务唯一键。超时不能直接当失败处理，应查询最终状态。

远程调用必须设置合理超时，避免 for 循环调用，优先批量接口。

Redis key 命名遵循项目已有规范，必须设置过期时间，谨慎使用 `hgetall` / `smembers`。

## Java 运行环境

本机 Java 由 SDKMAN 管理，同时存在 Java 8 和 Java 17。

运行 `java`、`mvn`、`gradle`、测试或构建前，必须先根据项目配置判断所需 JDK 版本。

禁止无脑使用默认 Java 环境。

## 完成前自检

开发完成前检查：

1. 功能是否满足需求。
2. 是否修改无关代码。
3. 是否影响已有兼容性。
4. 是否引入性能或稳定性风险。
5. 是否符合项目规范。
6. 编译是否成功。
7. 集成测试是否全通过，且结果是否符合本次需求预期。
8. 是否已执行 `codegraph sync`，或说明 CodeGraph 初始化/同步失败原因。
9. 是否存在未说明的本机环境前提。

无法完成编译或集成测试时，不能声称开发完成；必须说明未验证原因和剩余风险。
