# Dev

## 定位

`dev` 负责完成一次预期清楚的代码变更。它接受两种输入：

1. 已有稳定产物：消费已确认的 `design.md`、接口契约和测试规格，不重新定义上游事实。
2. 边界清楚的小需求：直接使用用户描述和当前代码形成必要 spec，不强制产出独立文档或重复确认。

测试或真实反馈必须与实现风险匹配，但显式调用 `dev`、二开、有 API 或没有 API，都不能单独决定是否新增测试代码或采用哪种 TDD 形式。

涉及实际代码修改、生成代码或调整接口时，编码前加载 `coding-standards`。

## 输入判断

开始前确认：

1. 要改变的行为、不能改变的范围和验收结果。
2. 相关接口、字段、数据结构、既有行为和外部条件。
3. 当前工作区已有修改及其意图。
4. 可执行的主验收、补充证据、关键阻塞和停止条件。

用户描述和现有资料已经足以安全执行时，直接把它们作为当前 spec，不为形式完整重复确认。缺失信息会实质改变结果时才询问；需要新增稳定设计事实或复杂测试规格时，分别返回 `design` 或 `test-design`。

注释、格式、命名、常量、构建配置等不改变用户可观察行为的修改，可以确认范围后直接执行；一旦识别到行为变化，补齐对应预期和验证。

## 验证策略

先选择能证明本次正确性的主验收，再判断是否需要新增测试代码和测试先行：

1. 新增或改变 API、OpenAPI 的用户可观察行为时，以 `it-test` 的真实 HTTP 目标集测和相关回归作为最终 Green 验收；已有 IT 能覆盖时直接复用或更新。
2. 复杂算法、多分支、状态机、难穷举边界、多入口复用逻辑，或没有合适 API 入口的内部功能，按需使用 `unit-test` 建立白盒反馈。
3. 格式、时间展示、注解、常量、一对一映射、明确返回结构等简单聚焦修改，优先直接实现后运行主验收，不为形式新增测试或获得 Red。
4. 已有测试能够充分保护受影响行为时直接复用，不创建重复测试。
5. 新增或改变复杂、高风险行为、问题难稳定复现、影响多入口或重要回归契约，且测试能够稳定复现和判断结果时，提高测试先行权重。

单测、Mock、Stub、编译和静态检查不能替代本次正确性所依赖的真实链路；反过来，也不能因为存在 API 就机械新增集测文件。

## 开发执行

### 准备

1. 读取项目规则、相关代码、已有测试和当前工作区变化。
2. 有稳定产物时读取完整设计、接口契约和测试规格；否则使用当前会话 spec。
3. 按功能、接口、数据或文件边界拆分最小可验证单元。
4. 为每个单元明确影响文件、主验收、补充证据和停止条件。

### Sub-agent 编排

存在多个独立单元时，判断是否调用 `subagent`：

1. 每个单元必须有独立规则、文件范围和验证方式。
2. 共享工作区默认串行；文件、测试数据、端口、数据库和外部环境互不影响时才并行。
3. Sub-agent 不得自行改变设计事实和验收预期。
4. 主会话复核实际修改，并统一执行整体验证。

### 反馈与实现循环

对每个最小可验证单元：

1. 运行可用的已有测试、目标调用或检查，建立必要的修改前基线。
2. 判断是否需要新增测试代码，以及是否需要先通过断言获得目标 Red；需要测试时选择
   `it-test`、`unit-test` 或两者组合，并在编辑或运行对应测试前完整加载所选
   Skill。测试文件、数据、环境前置和完成边界服从所选 Skill，不用通用测试习惯替换其
   已明确的专项约束。
3. 测试先行有价值时，先确认新增行为测试因目标能力缺失而失败；不需要时说明简单性和最终验收依据后直接实现。旧行为保护测试应在修改前通过。
4. 加载 `coding-standards`，实施满足当前 spec 的最小代码修改。
5. 运行主验收和相关回归，确认结果、兼容性、数据和副作用符合预期。
6. 高风险内部逻辑仍缺少证据时补白盒测试；真实链路仍未验证时不得用补充证据宣布完成。
7. 所有相关反馈通过后再做必要重构。

测试规格定义需求预期，代码实现只能用于补充风险判断，不能反向改变已确认预期。发现上游事实错误时返回 `design` 或 `test-design`。

## 二开与回归

1. 回归范围只覆盖本次修改可能影响的既有行为，不扩张成全系统补测。
2. 先查找已有测试和真实验证入口；覆盖充分时复用，覆盖不足时只补有回归价值的缺口。
3. 默认不修改旧回归预期；只有已确认需求明确改变旧行为时，才说明依据并更新。
4. API 二开是否新增集测，取决于本次正确性是否依赖真实契约和链路、已有覆盖是否充分及回归价值；不能只按“有 API”判断。
5. 没有 API 入口也不自动要求新增单测；按内部行为复杂度、已有覆盖和可验证方式判断。

## 停止并补充稳定产物

出现以下任一情况，停止实现并补充上游事实：

1. 新模块、跨多个模块或跨系统状态链路，当前 spec 无法稳定承载。
2. 需要新增独立数据结构、公共契约或长期设计事实。
3. 回归范围、权限、数据、上下游或副作用条件无法可靠判断。
4. 用户目标与现有规则、设计或测试预期存在未解决冲突。

## 完成门禁

完成前确认：

1. 所有已确认行为都有可判断的验证证据，不要求机械映射为新增测试方法。
2. 本次风险要求的真实 API、鉴权、数据、状态或副作用链路已实际验证；无法执行时明确停在验收阻塞状态。
3. 新增或受影响的测试代码与运行方式符合所选测试 Skill；能够执行的集测、单测及已有
   回归已按策略实际运行并通过。
4. 项目存在适用编译或构建命令时已实际运行并成功。
5. 改动范围、设计一致性、兼容性和工作区已有修改已复核。
6. 使用 Sub-agent 时，节点产物已由主会话复核并重新完成整体验证。
7. 未验证项、原因和残余风险已明确说明。

## 输出要求

说明：

1. 当前 spec 和验收来源。
2. 修改的生产代码、测试代码及范围。
3. 主验收、补充证据和是否新增测试代码的判断依据。
4. 实际运行的命令、测试和结果。
5. 未验证项、残余风险和原因。

## 禁止事项

1. 在缺失信息会实质改变结果时猜测实现。
2. 擅自补写或改变已确认的设计和测试预期。
3. 通过删除断言、放宽断言、跳过测试或改写旧预期制造通过。
4. 用补充证据替代本次风险要求的真实验收。
5. 关键验证或适用编译失败时声称完成。
