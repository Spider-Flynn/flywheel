# Debug

## 定位

`debug` 负责定位问题并形成修复建议，不默认执行修复。它的目标是找到可验证的根因和触发条件，并在条件充分时给出可执行修复方案。

没有根因前，不提出具体修复方案；没有证据前，不把猜测写成结论。根因已验证且正确预期清楚时，应给出修复方案；条件不足时明确缺少什么，不能只停在“建议进入 fix”。

## 输入

优先收集：

1. 用户描述的异常现象。
2. 错误日志、堆栈、失败测试和命令输出。
3. 复现步骤、输入参数、环境信息。
4. 最近变更、相关配置、相关代码路径。
5. 已尝试过的修复或排查动作。

## 排查流程

1. 完整阅读错误信息，不跳过堆栈、行号、错误码和上下文。
2. 尝试复现或确认触发条件。
   - 如果用户已经提供了充分的复现信息和证据，优先使用已有信息定位，不需额外构造。
   - 如果触发条件不确定、涉及复杂数据链路或多层调用链，但可以从代码入口构造最小复现场景，可以写一个最小复现测试来锁定触发条件；复现测试只用于收集证据，不进入 TDD 循环。
   - 不需要复现测试的情况：用户已给出足够清晰的错误日志、堆栈、复现步骤且可追踪到具体代码路径。
3. 如果无法复现，说明已有证据和缺口，不猜测修复。
4. 检查最近变更，判断可能影响路径。
5. 沿数据流、调用链或配置链路向上追溯，找到异常值或异常状态的来源。
6. 查找同项目内相似的正常实现，对比差异。
7. 提出单一根因假设，并用最小验证动作验证。
8. 输出根因、证据和影响范围；根因已验证且正确预期清楚时，给出修复方案和验证方法。

## 假设验证规则

1. 一次只验证一个假设，不能同时改多个变量。
2. 验证动作必须最小化，能证明或推翻假设即可。
3. 假设被推翻时，回到证据重新分析，不在失败修改上继续叠加。
4. 连续三次根因假设被推翻时，停止在同一路径继续尝试，判断是否是设计、架构、测试数据或环境前提错误。

## 多层链路排查

当问题跨 Controller、Service、DAO、DB、Redis、MQ、外部接口或构建环境时，按边界收集证据：

1. 每层输入是什么。
2. 每层输出是什么。
3. 配置或上下文是否正确传递。
4. 哪一层开始出现错误。
5. 是否存在测试数据或环境状态问题。

## 修复方案

根因已验证后，除非正确预期、设计事实或必要环境仍不明确，否则给出：

1. 修复目标，以及错误行为与正确行为的差异。
2. 对应根因的最小修改点、涉及范围和不应改动的行为。
3. 建议新增或复用的回归测试、原始触发路径和验证方法。
4. 兼容性、副作用与残余风险；存在多个可行方案时说明首选方案及取舍。

只给出与现有证据一致的方案。未实际修改或验证时，明确标记为“修复方案”，不得写成已经修复。

## 后续分流

| 结论 | 下一步 |
| --- | --- |
| 已定义预期被违反 | 给出修复方案，后续进入 `fix` |
| 需求或规则需要新增/澄清 | `dev` 或 `design` |
| 设计事实缺失或冲突 | `design` |
| 测试预期、测试用例或回归范围错误 | `test-design` |
| 只是环境、数据或使用方式问题 | 输出处理建议，不改代码 |
| 根因仍不清 | 说明阻断和还需要什么证据 |

## 禁止事项

1. 不要边猜边改。
2. 不要同时尝试多个修复。
3. 不要只修症状，不追根因。
4. 不要删除、放宽或跳过测试来制造通过。
5. 不要在没有根因时提出具体修复方案。
6. 不要把无法复现的问题写成已确认修复。
7. 不要把尚未执行或验证的修复方案写成已完成修改。
