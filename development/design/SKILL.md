# Design

## 定位

`design` 按顺序完成 Spec 澄清，并逐步产出或修正 `design.md` 和必要接口契约材料。它不生成测试用例、不进入编码、不拆执行任务、不修 bug、不做交付收尾。

设计阶段只围绕当前需求、功能点、规则、核心数据、数据源规则、处理流程和接口结构展开。按当前场景利用已有材料或必要现状，先确认能够自行获得的事实，只把必须由用户决定或补充的信息集中提问，不用猜测补齐设计结论。

设计产物必须足以支持后续撰写需求级测试用例。只提供可判断验收结果的功能规则和接口契约，不展开具体测试数据、测试代码或回归测试组织。

## 输入

优先收集以下信息：

1. 用户需求或变更说明。
2. 已确认的功能点、变更点、边界和不做范围。
3. 相关项目上下文、已有实现、接口、表、对象、字段和外部文档。
4. 已存在的 `design.md`、接口契约材料或历史设计结论。
5. 用户明确说不能做、暂不做或边界不清的内容。

## 模板使用

先按当前需求自然组织技术设计，不机械套固定结构。需要形成跨阶段稳定设计产物、项目没有更权威模板，且统一结构能降低遗漏风险时，再读取 `assets/technical-design-template.md`，选择与当前需求有关的章节。

模板只约束最终设计文档的组织方式，不改变本 skill 的确认顺序。使用后产出当前有效的设计事实，删除无意义空章节和占位内容。

需要生成接口契约时，读取 `references/interface-document-rules.md`，根据接口实际内容自然组织，不套固定模板。

只加载本次需要的资源。

## 信息获取边界

1. 提问前先吸收用户提供的需求、材料和已经确认的结论，再按当前场景补充会影响设计的必要信息。
2. 从 0 到 1 的功能不预设存在可复用实现。优先确认业务规则、系统边界、数据来源、上下游契约、技术与运行约束；只有项目现有规范或公共能力会影响设计时，才读取对应材料。
3. 二开、改造或兼容现有功能时，读取直接相关的已有设计、入口代码、DDL、任务配置和接口契约，沿本次涉及的调用与数据路径确认现状。
4. 只获取回答当前设计问题所需的最小范围，不为完整理解项目无限扩展上下文。
5. 核心数据和数据源规则可以依据需求材料、权威文档、DDL、上游任务、接口契约、配置、代码或查询结果确认；不能用名称、单次样本或未经验证的经验推断未证实的规则。
6. 当前可用信息能回答的事实自行整理并注明来源，不要求用户重复提供；确实缺少、不可访问或必须由用户决定的信息再集中提问。
7. 后续信息获取会明显增加上下文时，提醒用户可以按需 compact；compact 不是继续设计的门禁。

## Spec 顺序

设计事实按以下依赖顺序收敛，不能用下游方案反推未确认的上游规则。这个顺序是逻辑依赖，不代表每个阶段必须占用一个独立交互轮次；可以提前获取和整理多个阶段的信息，再集中确认。

1. 确定具体需求。
2. 将需求划分为具体功能单位，例如接口清单或其他功能单位，并明确接口数量和功能。
3. 确定每个功能的规则、限制、适用条件和行为边界。
4. 确定相关表、对象、核心字段、数据关系和表结构信息来源。
5. 确定会影响当前设计的数据源规则，包括数据身份与权威来源、产生方式、业务粒度、唯一性、时间与分区语义、全量/增量/快照属性、更新删除、迟到回补、重跑覆盖、完整性和可用时点。
6. 基于已确认的数据源规则梳理具体实现流程，明确运行时取数范围、处理顺序、校验判断、数据读写、接口或字段变更，以及用户补充的实现注意事项。
7. 按需产出接口契约材料，例如接口字段、请求响应结构或接口文档。
8. 制定待办清单，记录未确认、待补充或待处理的问题。

## 取证与提问

1. 梳理后把信息分为：可用材料已证明的当前事实、用户已经确认的目标规则、合理推测、必须由用户决策或补充。前两类直接形成确认稿；后两类不能写成确定事实。
2. 现有代码和配置只证明当前行为，不自动代表本次目标规则。需求已要求沿用时直接记录；是否沿用本身会改变结果且没有依据时，作为一项决策与其他问题合并确认。
3. 输出时分开呈现当前事实、已确认目标、合理推测和待决策事项，并为当前事实注明来源。不要在当前事实中使用“应当”“必须”等目标性措辞，也不要补写证据中没有的子规则。
4. 只询问缺少答案会实质改变设计的问题。当前可用的需求材料、权威文档、代码、DDL、配置、接口契约或已有设计能够回答的问题，先自行确认。
5. 按决策依赖组织待确认事项。每轮集中询问所有前置条件已经确定、彼此不依赖的事项；依赖本轮答案的事项留到下一轮，不能提前假设。
6. 每个待决策事项给出推荐选择、关键依据和不同选择的主要影响。证据不足以形成推荐时明确说明，不为方便确认而伪造确定答案。
7. 用户回答后重新判断剩余事项的依赖和必要性，再形成下一轮；不退化为逐题问答，也不把前置条件未确定的问题塞进当前轮次。
8. 用户一次回复可能同时修正多个阶段；同步识别全部影响，不只处理当前标题下的一点。
9. 不询问“是否进入下一阶段”这类纯流程问题。当前依赖已满足时直接继续；需要用户确认时确认设计事实本身。
10. 用户没有回答的问题继续标为待确认。相邻回复、默认值、代码现状和他人说明都不能替代用户未作出的业务决策。

## 模块边界

1. 功能规则回答“功能必须表现成什么样”，只写功能本身、规则、限制、适用条件和用户可感知的行为边界，服务前端、后端、具体流程设计和后续开发线程；不写表字段、查询顺序或代码实现。
2. 核心数据回答“功能涉及哪些稳定数据结构”，只写表、对象、核心字段、数据关系和已有结构的信息来源；不写运行时取数和处理顺序。
3. 数据源规则回答“这些数据以什么身份和规则存在”，只写会影响当前设计的数据来源、产生与变化语义、粒度、时间、唯一性、完整性和可用性；不提前写本功能如何查询、组合和写入。
4. 具体流程回答“基于已确认的数据事实如何实现功能”，写运行时取数范围、核心处理逻辑、执行顺序和用户补充的实现注意事项，服务后端开发者和开发线程。
5. 同一事实只在一个模块完整描述。用户补充的信息按性质归入功能规则、核心数据、数据源规则或具体流程；尚未确认的信息进入待办清单。

## 数据源规则确认

1. 只确认会影响当前设计选择的源数据事实，不为完整画像无限追溯上游。
2. 数据源不局限于数据库表；已有接口、消息、文件、缓存和外部系统数据都按同样原则确认。
3. 优先依据权威文档、DDL、上游任务或代码、接口契约、配置、数据负责人说明和能够回答目标问题的查询结果；记录结论的信息来源。
4. 区分已确认事实、合理推测和暂时无法验证的信息。不能从字段名、分区名、单个分区或少量样本直接断定全量/增量、唯一性或跨时点变化规则。
5. 多数据源组合时，必须确认各自粒度和关联基数、关联键稳定性、时间对齐方式，以及重复、缺失和未匹配数据会不会造成结果放大或丢失。
6. 数据源规则无法确认时，将问题写入待办清单；依赖该规则的取数、去重、关联和写入方案不得伪装成已确定结论。

## 阶段推进与确认

1. 模块是设计事实的逻辑检查点，不是强制独立交互轮次。相邻模块已有充分证据且没有依赖冲突时，可以合并输出确认稿和待确认事项。
2. 总体需求存在实质歧义时先确认需求；边界已经明确时，直接继续梳理功能单位、数据和方案流程。
3. 输出确认稿时，按需分开呈现总体需求、功能划分、功能规则、核心数据、数据源规则、具体流程和接口契约，让用户能够识别每项事实的归属和依据。
4. 未确认的上游事实可以继续调查，但不能据此固化下游方案；阻断后续问题内容的依赖项单独先问，其余问题集中收口。
5. 用户确认一批设计事实后，一次性更新 `design.md` 中所有受影响章节并继续推进，不为每个章节分别回写和汇报。
6. 接口契约确认后，按需产出或更新契约材料，并保证它与 `design.md` 中的接口清单、功能规则、核心数据、数据源规则和具体流程一致。
7. 用户补充的信息足以消除待办时，直接写回正文并清除待办；未被回答的事项继续保留。

## 修改设计流程

1. 先阅读完整 `design.md`，理解整体结构和各章节关系。
2. 判断本次修改影响哪些目标、规则、数据、流程、接口和待办清单。
3. 同步更新所有受影响章节，避免只改局部导致信息不一致。
4. 如果新结论推翻旧规则，删除或改写旧表述，不保留冲突描述。
5. 如果用户回答消除了待办清单中的事项，把结论写回正文并清除该待办。

## 接口契约规则

1. 接口契约必须在功能规则、核心数据、数据源规则和具体流程基本明确后产出。
2. 新增接口要贴合真实项目已有接口风格，明确请求、响应、字段含义和错误边界。
3. 二开接口必须先读取或获取原有接口结构，再根据该功能规则判断字段保留、删除、新增和含义变化。
4. 不确定字段是否该删、是否兼容旧响应、是否需要新增请求或响应信息时，先向用户询问，不先产出接口契约。
5. 接口文档按 `references/interface-document-rules.md` 的规则产出；用户已指定其他格式时按用户要求产出。
6. `design` 负责确认接口信息并产出契约；具体文件结构由 `references/interface-document-rules.md` 负责。

## 设计文档命名与存放

设计文档文件名使用 `模块名/功能名 + 设计.md` 格式，例如 `资产查询设计.md`、`演练任务设计.md`。在 skill 说明中统一用 `design.md` 指代设计文档，但实际产出使用汉字命名。

存放规则：

1. 设计文档和接口契约材料默认产出到 `docs/powers/`。
2. 单模块：在 `docs/powers/` 下产出 `模块名设计.md`。
3. 多模块：先判断各模块的复杂度和信息量。复杂度足够或信息量大到合并会造成混乱时，才拆分多个设计文档，每个模块产出自己的 `模块名设计.md`；复杂度低、信息量少的模块可以合并到一份设计文档中。
4. 模块内存在独立复杂功能（牵扯大量规则、数据和流程）：在 `docs/powers/` 下产出 `功能名设计.md`。

## 文档产出规则

1. 技术设计是结果导向文档，只保留当前设计已经确认的有效结论。
2. 不记录设计过程、讨论轨迹、提问顺序、旧方案替换过程或临时判断。
3. 一批设计事实确认后，一次性写入正文所有受影响章节；后续确认继续补充和修正。
4. 修改设计文档时，必须同步更新受影响章节，保证全文一致。
5. 接口契约材料如果单独产出，必须与已确认的接口清单、功能规则、核心数据、数据源规则和具体流程一致。
6. 同一事实只在所属模块完整描述，其他模块需要使用时引用结论，不重复展开。

## 设计产出自检

完成前必须自检：

1. 是否按需求、功能划分、功能规则、核心数据、数据源规则、具体流程、接口契约和待办清单的依赖关系收敛事实。
2. 是否按场景利用了可用信息：从 0 到 1 未强求现有实现，二开已核对必要现状，并避免把能够自行确认的问题抛给用户。
3. 当前轮次是否覆盖所有前置已确定且彼此独立的决策，每项是否给出有依据的推荐和主要影响；依赖未满足的事项是否留到后续轮次。
4. 已确认的一批事实是否已一次性写入或更新到 `design.md` 所有受影响章节。
5. 接口清单、功能规则、核心数据、数据源规则、具体流程、接口契约和待办清单是否互相一致。
6. 是否存在待填占位、模糊词或可被两种方式解释的规则。
7. 设计文档和接口契约材料的位置是否清楚。
8. 功能规则、核心数据、数据源规则和具体流程是否职责清楚，是否存在同一事实跨模块重复描述。
9. 功能规则和接口契约是否足以让 `test-design` 判断输入、预期结果和行为边界。
10. 取数、去重、关联和写入方案依赖的数据源规则是否已有证据；未确认项是否保留为待办而非确定结论。
11. 是否清楚区分当前事实、已确认目标、合理推测和待决策事项，避免把代码现状误当成目标规则，或补写证据中没有的子规则。
12. 是否把用户未回答的问题、合理推测或他人说明错误升级成已确认的业务事实。

## 禁止事项

1. 不要写生产代码。
2. 不要只改局部文档而忽略整体一致性。
3. 不要把接口详情大段塞进设计正文；接口详情应单独维护。
4. 不要为了完整而扩写无关背景。
5. 不要把未确认规则伪装成已确认结论。
6. 不要把待办事项伪装成当前已确认设计。
7. 不要编写测试用例、测试代码或生产代码。
