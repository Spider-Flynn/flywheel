# CR

## 定位

`cr` 不是默认修复入口，也不是单纯找茬的代码审查。它用于用户对 AI 产物提出问题后，进行解释、对齐和分流。

本 skill 的目标是回答“为什么这么做、有没有风险、是否需要改、按什么粒度改”。

## 典型触发

1. “为什么这里用 A 不用 B？”
2. “这样会不会有问题？”
3. “这里是不是漏了某个场景？”
4. “这个颗粒度是不是太粗？”
5. “我觉得这个实现不太对。”
6. “这里应该补一下吗？”
7. “这个判断应该放在 Controller 还是 Service？”

## 执行流程

1. 完整读取用户反馈，不急着同意或修改。
2. 定位用户提到的代码、设计、测试或上下文。
3. 解释当前实现意图和相关约束。
4. 判断用户反馈属于哪类问题。
5. 如果只是理解问题，直接解释并给出判断。
6. 如果存在潜在风险但证据不足，转 `debug`。
7. 如果确认已有预期被违反，转 `fix`。
8. 如果确认需要新增或调整功能规则，转 `dev`。
9. 如果影响设计事实，转 `design`。
10. 如果需求级测试预期或回归范围有问题，转 `test-design`。
11. 如果只是测试代码覆盖不足，说明应在 `dev` 或 `fix` 中补 `unit-test` 还是 `it-test`。

## 反馈处理规则

1. 用户反馈先理解再验证，不能表演式赞同。
2. 外部审查意见必须结合当前代码、设计和项目规则判断是否成立。
3. 不清楚的多项反馈必须先澄清，再执行；不要先做一半。
4. 反馈如果违反已有设计或用户决策，先向用户说明冲突，不直接改。
5. 正确反馈按风险排序处理：阻断问题、简单修正、复杂调整。
6. 每个修正都要有对应验证，不把“已修改”当作“已解决”。

## 分类标准

| 用户反馈类型 | 处理方式 |
| --- | --- |
| 询问实现原因 | 解释设计取舍和代码事实 |
| 怀疑有风险但未证实 | 转 `debug` 收集证据 |
| 明确 bug | 转 `fix` |
| 新增或澄清功能预期 | 转 `dev` |
| 影响设计文档、接口规则或核心数据 | 转 `design` |
| 测试预期、测试用例或回归范围有误 | 转 `test-design` |
| 仅测试代码覆盖不足 | 转 `dev` 或 `fix`，调用对应测试 skill |
| 单纯风格偏好 | 说明是否值得改，不默认执行 |

## 对齐要求

1. 先复述用户关注点，确保理解一致。
2. 回答必须基于代码、设计文档或项目规则。
3. 不能用泛泛的“这样更好”代替技术理由。
4. 可以提出优化方案，但要说明收益、风险和是否值得做。
5. 需要改代码时，先说明应转入哪个 skill。

## 禁止事项

1. 不要表演式赞同。
2. 不要在没看上下文时判断对错。
3. 不要把用户的新预期误判成 bug。
4. 不要把真实 bug 包装成功能优化。
5. 不要默认改代码；先对齐，再分流。
6. 不要忽略外部审查中的阻断或重要问题。
