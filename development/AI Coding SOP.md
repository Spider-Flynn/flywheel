# Powers AI Coding SOP

## 一、核心原则

1. 人负责业务全局、目标、边界和验收；AI 只接收当前工作需要的业务事实。
2. AI 修改代码前先读取当前实现、工作区变化、项目规则和相关契约，不把现有修改默认视为错误。
3. 复杂需求按设计与开发职责拆分会话，小需求在干净的项目上下文中直接完成。
4. 跨会话只传递下一阶段需要的有效事实，不传完整探索过程。
5. 测试或真实反馈先于无约束实现；主验收证据按用户可观察风险选择，补充证据不能替代关键真实链路，TDD 的具体形式由行为风险决定。
6. 实现拆解、执行顺序和 Subagent 编排由 AI 决定，SOP 不规定 task 文档和固定颗粒度。
7. 小修改默认不维护外部过程文档，直接基于当前代码、项目规则和对话 Spec 完成。
8. Development Powers 只服务于软件开发任务并提供具体实践边界；非开发任务不因位于项目目录、修改文件或用户反馈而触发 Development Powers，开发中的普通低风险任务也可以不用 Skill。
9. 业务事实必须来自当前对话、PRD 或其他可信材料；AI 发现缺口时先提问，不自行补写假设或为凑齐范围而发明排除项。

## 二、开发 SOP

### 2.1 新项目、新模块和复杂需求

```text
[人：理解业务、确定目标和验收]
                 ↓
[会话 A：设计]
读取当前状态
→ 补齐必要业务事实
→ 技术设计
→ 产出 design.md
→ 设计新功能与回归测试预期
→ 产出 test.md
                 ↓
[会话 B：开发基会话]
加载项目规则 + 当前代码 + design.md + test.md
→ 独立启动服务并基于 test.md 编写真实 HTTP 灰盒 API 集成测试
→ 在 IT 文件内补齐或维护测试数据、身份和外部条件
→ 运行测试建立修改前反馈
→ TDD 开发
→ 测试通过
→ 整体编译、集成测试和回归验证
→ 人工 Review；发现问题时经 cr 判断后转入 fix、debug 或 dev，并重新完成验证与人工 Review
→ 按授权 Commit / 部署 / 提测
→ 按需 Compact B，保留为后续基会话
→ 后续独立小问题从该基会话分叉定向会话
```

核心行为：

- A 中由人确认业务目标、范围和验收；AI 读取当前状态后产出 `design.md`、`test.md`。
- `design.md` 记录本次新增或变化的技术事实；`test.md` 记录新功能、边界、异常和回归预期。
- B 基于 `test.md` 优先编写灰盒 API 集成测试：服务独立启动，IT 文件通过真实 HTTP 调用本地 API，并在文件内就近维护账号、权限、业务数据和外部条件；无法确认合法性时集中向用户索取。
- 没有适合的 API 入口时，由 AI 选择白盒测试、编译、真实调用或结果回查，不强行编写无效集测。
- AI 自主决定整体实现、内部拆解和 Subagent 编排；B 负责代码整合和最终验证，测试与编译通过后由人进行 Review。
- `design.md`、`test.md` 是当前任务产物，不作为持续维护的项目知识，也不因后续小修改自动更新。

### 2.2 小需求和局部修复

```text
进入项目基会话或从 B 基会话分叉定向会话
→ 读取当前代码、工作区变化和项目规则
→ 在对话中明确增量 Spec
→ 明确主验收、补充证据、关键阻塞和停止条件
→ 选择最小充分反馈
→ 判断是否需要测试先行获得 Red
→ 修改
→ 验证
→ 人工 Review；发现问题时经 cr 判断后转入 fix、debug 或 dev，并重新完成验证与人工 Review
→ 按授权 Commit / 提测
```

小需求默认：

- 不创建 `design.md`、`test.md` 和任务文档。
- 不重新加载与当前修改无关的完整设计材料。
- 不因为显式 `dev`、二开、有无 API 自动进入完整流程或新增集测文件；本次正确性依赖真实 API 契约、鉴权、装配、数据或外部副作用时，必须完成真实验证或明确停在验收阻塞状态。
- 不为格式、注解、常量、一对一字段映射等机械修改强制新增测试。
- 新增或改变 API、OpenAPI 的用户可观察行为时，最终必须通过真实 HTTP 目标集测和相关回归验收；已有 IT 能覆盖时直接复用或更新，不为形式新建测试文件。
- 必须获得编译、已有测试、目标调用、序列化检查或结果回查等最小充分反馈。

## 三、上下文与 Subagent

### 3.1 上下文

- 新会话先读取当前代码和项目规则，再读取阶段产物；文档不能覆盖代码现实状态。
- 执行上下文只保留当前目标、有效设计、测试预期和外部条件，不加载完整业务画像和探索记录。
- 跨会话只传递有效结论、产物路径、验证结果和未完成事项。
- 上下文接近饱和时先收敛有效结论，再从干净基线继续工作。
- 定向会话只处理当前问题，并尊重工作区中已有的有效修改。

### 3.2 Subagent

Subagent 用于可以独立完成、又不需要长期保留在主会话上下文中的工作。主会话规划职责、依赖、写入范围和汇合点，只发送最小必要上下文，并复核和整合结果。

AI 可以使用一个或多个 Subagent，不为并行而并行。主线立即依赖、范围很小、共享核心文件或协调成本高于收益时，由主会话直接完成。

## 四、横切规则与 Powers

### 4.1 STDD

```text
读取现状
→ 理解已有变化和本次意图
→ 形成增量 Spec
→ 明确主验收、补充证据、关键阻塞和停止条件
→ 建立测试或真实反馈
→ 判断是否需要先获得目标 Red
→ 实现
→ 验证
→ 人工 Review
```

修改代码前先判断获得目标 Red 是否能显著降低实现错误或回归风险。新增或改变复杂业务行为、状态流转、计算逻辑、错误处理，问题难稳定复现、影响多入口或回归代价高时，提高 TDD 权重；格式、时间展示、一对一字段映射、明确返回结构等简单聚焦修改，可以直接实现后验收，不为形式获得 Red。未选择测试先行时说明判断依据，验证仍不可省。

验证形式服从本次风险。新增或改变 API、OpenAPI 的用户可观察行为时，以真实 HTTP 目标集测和相关回归作为最终 Green 验收；Mock、Stub、单测、编译和静态检查只能补充，不能把尚未完成的真实验收改写为已经验证。

已有测试是行为证据。除非需求明确改变旧预期，不通过删除、放宽或随意改写断言制造通过。

### 4.2 人工 Review 与交付

代码完成并通过本次需要的测试、编译和其他验证后，由人进行 Review，检查：

- 修改是否符合用户目标、`design.md` 和当前 Spec。
- 是否超出授权范围或改动无关代码。
- 是否保留当前工作区中已有的有效变化。
- 边界、异常、兼容性和副作用是否处理完整。
- 是否符合项目结构和编码规范。
- 测试和验证结果是否真实，是否存在未覆盖项。

人工 Review 发现问题后，先由 `cr` 解释和判断，再按问题性质转入 `fix`、`debug`、`dev`、`design` 或 `test-design`；代码变化后必须重新完成与风险匹配的验证和人工 Review。

Commit、push、PR、部署和外部发布遵循用户授权和项目规则。

### 4.3 Powers 全局拓扑

```text
用户任务
  │
  ├─ 清楚、局部、低风险 ─────────────→ 直接处理，无需 Skill
  │
  ├─ 业务或设计信息不足
  │    ├─ 业务全局与上下游 ──────────→ biz
  │    ├─ 技术规则与 design.md ──────→ design
  │    └─ 测试预期与 test.md ────────→ test-design
  │
  ├─ 开发与问题处理
  │    ├─ 新增或调整功能 ────────────→ dev
  │    ├─ 根因未知，需要定位和修复建议 ─→ debug
  │    ├─ 已有实现违反确认预期 ──────→ fix
  │    └─ 需要解释、判断或人工复核 ──→ cr
  │
  └─ 专门实践
       ├─ 生产代码规范 ──────────────→ coding-standards
       ├─ 白盒反馈 ──────────────────→ unit-test
       ├─ 灰盒 API 集成反馈 ─────────→ it-test
       └─ 独立上下文分叉 ────────────→ subagent
```

使用规则：

1. “无需 Skill”是合法结果。
2. `biz`、`design`、`test-design`、`dev`、`debug`、`fix`、`cr` 是用户入口 Skills，目标明确时建议显式调用；入口不明确时根据当前目标和各 Skill 的触发边界选择。
3. 一次优先只选择当前必要入口，不堆叠多个入口 Skills。
4. `coding-standards`、`unit-test`、`it-test`、`subagent` 是流程内置 Skills，由当前入口在实际需要时加载；“内置”只表示在 SOP 中的协作位置，不限制用户直接调用或模型在目标明确时隐式触发。只有实际编写生产代码时固定加载 `coding-standards`，其余按风险和收益判断。
5. 显式 `dev`、二开、有无 API 不自动触发设计文档、测试文档、新增测试代码或 TDD；这项留白不用于跳过本次风险要求的真实验证。
6. 固定流程、模板和示例只在能够降低明确风险时使用，其余部分保留留白。
7. 主会话负责用户交互、公共决策、Subagent 编排、结果整合和最终交付。
